Project 03 — Manipulation & Safety

UR3e — Pick-and-Place Cell

A Universal Robots UR3e with a Robotiq gripper, an overhead camera and a web dashboard. It finds cubes on a table, works out which ones it can actually reach, refuses the ones it can't, and sorts the rest into a marked drop zone.

Runs from a bare ROS 2 Humble install — no FastAPI, no rosbridge, nothing to pip install.

Sees, decides, acts

Sees. An overhead camera feeds a colour-segmentation pipeline that finds every cube and projects it onto the table plane through the camera transform. Each cube gets an ID that survives the arm passing overhead — which sounds like a detail until you realise the orchestrator has committed to picking "cube 4" and cannot have that renamed halfway through the cycle because a shadow briefly split one blob into two.

Decides. The table is divided into three zones by radius from the base: too close, workable, too far. Cubes are classified on sight, and anything outside the workable band is refused rather than attempted. A robot that declines an impossible task is more useful than one that tries it and faults out.

Acts. Each cycle runs a state machine: approach, straight-line descent, grasp, lift, transfer, straight-line place, release, depart. Descents and lifts are Cartesian so the tool travels vertically rather than arcing sideways into the object it is reaching for. Every cube not currently being picked is published to MoveIt as a collision object, so the arm plans around the others instead of through them.

Full multi-cube sweep — Gazebo on the left, the operator dashboard on the right showing live state, detected cubes with their reach classification, joint positions and the activity log.

The emergency stop — worth the whole project

This is the part I'd want to talk through in an interview, because the obvious implementation does not work and the reason is instructive.

Engineering note — cancelling isn't stopping

Cancelling the in-flight action goals is necessary but not sufficient. A trajectory that has already been handed to the controller keeps executing regardless of what happens to the goal that produced it — the arm carries on for several radians while your "stop" sits there having successfully cancelled nothing that matters.

The stop also has to command the controller to hold its current position. That is the part that actually brings the arm to rest. Measured drift after a stop: 0.0001 rad.

It then latches. Every command except reset is refused until the latch is explicitly cleared. This is deliberately a different thing from stop, which is a tidy recovery — reopen the gripper, drive home. Tidying up is exactly the wrong response to an emergency: if someone hit that button, the last thing you want is the arm helpfully travelling back to its home pose through whatever caused the emergency.

Tasks

TaskWhat it does

pick_toOne cube to coordinates typed in by the operator
spawn_cubeDrop a new cube into a free spot in the workable zone
home / retractMove to home, or park clear of the workspace
stopEnd the cycle tidily — reopen gripper, return home
estopHalt where it stands and latch
resetClear the latch, wipe the planning scene, return home

A dashboard with no dependencies

The interface is a ROS node plus Python's standard-library HTTP server. No FastAPI, no rosbridge, nothing to install — it runs from a bare Humble image. The browser polls a single JSON endpoint:

  • GET /api/state — orchestrator status, every detected cube with its zone, joint positions, drop-zone target, activity feed, liveness indicators for the orchestrator and camera
  • POST /api/task — {"task": "tidy"} or {"task": "pick_selected", "ids": [2,4]}

Task buttons disable themselves while the robot is busy. The emergency stop never does.

Testing what's true, not what the code believes

full_system_test.py runs about thirty checks covering startup, input validation, every task, emergency stop and reset. The design decision that matters: every physical claim is verified against Gazebo's own model state, not against the perception pipeline — because that pipeline is one of the things under test. A vision system asked to confirm its own output will always agree with itself.

That includes checking that placed cubes end up in different slots, not merely somewhere inside the drop square. Four cubes stacked in one corner satisfies a naive "is it in the zone" test perfectly.

Grasping in Gazebo Classic, honestly

Gazebo Classic's contact solver will not reliably hold a light box in a parallel gripper. The gripper does close on the cube physically, and a plugin fixes the nearest object to the tool once the driver knuckle passes a threshold, releasing when the gripper reopens. The motion looks and behaves like a real grasp; only the hold is plugin-assisted. Worth stating plainly — a portfolio that hides its simulator's limitations is telling you something about how it reports results.
